## Architecture rules
- The app is Flutter/Dart (root `lib/`); the previous React/Lovable web app lives in `legacy_web/` only as a behavior/design reference — do not add features there.
- The app is migrating to **Clean Architecture + Bloc**, one vertical slice at a time. **Orders are the first slice** (done): `lib/domain/` (entities, repository interfaces, ports, use cases — pure Dart, no Flutter/Supabase) ← `lib/data/repositories/` (in-memory + Supabase implementations of the domain interface) and `lib/features/orders/bloc/` (`OrdersBloc`: events → use cases → state). Dependencies only point inward; `test/architecture_test.dart` enforces it.
- Everything not yet migrated (session, catalog, notifications) still uses the `ChangeNotifier` controllers of `lib/shared/state/` (registered in GetIt, see the dependency-injection rule below) over repositories in `lib/data/repositories/`. Each repository has two implementations: in-memory (demo, used by the tests) and Supabase (real backend, enabled only when `AppConfig.hasSupabase`). Do not add a third source of truth. When touching one of those areas, prefer migrating it to the orders pattern instead of adding more `ChangeNotifier` code.
- Auth and cart are already migrated to cubits: `LoginCubit`, `RegisterCubit` and `UniversityVerificationCubit` (`lib/features/auth/bloc/`, with `AuthRepository`/`AuthException` in `lib/domain/repositories/`), and `CartCubit` (shared `LazySingleton` provided with `BlocProvider`) plus `CheckoutCubit` (`lib/features/buyer/cart/bloc/`). `CartCubit` replaced `CartController`; `CheckoutCubit` only validates and delegates the order to `OrdersBloc`. Login, register, Campus, cart and checkout screens read state from the cubit and never import `data/` implementations. Pending slices: `SessionBloc` and catalog.
- Payments are a Bloc slice: `PaymentBloc` (`lib/features/buyer/payment/bloc/`) → `StartPayment`/`CheckPaymentStatus`/`RetryPayment` → `PaymentRepository` (domain), with `SupabasePaymentRepository` (Wompi Edge Functions + Realtime) and `InMemoryPaymentRepository` (demo) registered in GetIt. Wompi keys and secrets live **only** in Supabase Edge Functions; the app only receives the checkout URL. Online orders are created with `payment_status='pending'` and the restaurant sees them only when `approved`; cash is `approved` with `cash_tendered`/`cash_change`. A rejection returns to the cart with the reason and allows retry; expiry cancels and refunds Gotas/coupon. `payments`/`payment_events` are audited and RLS-protected, and `wompi-webhook` verifies the checksum and is idempotent.
- HU-4 sigue el mismo patrón: Cubits (`flutter_bloc`) en `lib/features/**` → casos de uso en `lib/domain/usecases/` → interfaces en `lib/domain/repositories/` y puertos en `lib/domain/ports/`; las implementaciones viven en `lib/data/repositories/` y los adaptadores en `lib/shared/adapters/`, inyectados por GetIt. Cubits: `RateOrderCubit`, `RewardsCubit`, `MerchantBoxesCubit`, `NotificationsCubit`, `EarningsCubit`. Los widgets nunca llaman a Supabase directo. Con Supabase los avisos de pedido los crea la base (0022), así que el notificador de pedidos remoto no crea avisos locales.
- **Inyección de dependencias con GetIt (obligatoria):** todo se registra en `lib/app/di/injection.dart`, por módulos (`lib/app/di/modules/`: `core`, `data`, `domain`, `presentation`). Repositorios y puertos son `LazySingleton` tipados por su interfaz; los casos de uso son `Factory`; el `OrdersBloc` y los controladores son `LazySingleton`; los cubits de pantalla son `Factory` (con `param1` si necesitan datos de la pantalla). Las pantallas piden lo que necesitan con `getIt<T>()` y los Blocs con `BlocProvider`; para observar un controlador `ChangeNotifier` usan `context.watchController<T>()`. Solo `lib/app/di/` importa implementaciones concretas, y la única decisión Supabase/memoria (`AppConfig.hasSupabase`) está en `data_module.dart`. No hay `provider` ni `AppServices`. Las pruebas usan `makeServices()` (`getIt.reset()` + dobles de prueba), nunca un constructor solo para tests. `test/architecture_test.dart` lo hace cumplir.
- Visibility of restaurants/dishes must go through `isReachable` (radius + couriers nearby + campus-only) in `lib/domain/catalog_rules.dart`, exposed via `CatalogController.reachableRestaurants/reachableDishes` — single source for the distance rule.
- Business rules (pricing, filters, order transitions, scheduling, recommendations) are pure functions in `lib/domain/` with unit tests; widgets never duplicate them.
- Orders are shared by buyer, restaurant and courier through `OrdersBloc` → use cases (`lib/domain/usecases/orders/`) → `OrderRepository`. Screens dispatch events (`bloc.add(...)` or `await bloc.request(...)` when they need the result) and read via `context.watch<OrdersBloc>()`; they never touch repositories or mutate `Order`. Allowed transitions live in `kAllowedTransitions`; with Supabase the server (RPC) decides and every `result` code is translated by `lib/domain/order_errors.dart`.
- Merchant products are saved into the shared catalog repository via `CatalogController.saveDish`, so buyer screens and the radius rule see them without a second source.
- Mobile-first touch UI: shared pieces in `lib/core/widgets/`; yellow `#FCBD1A` primary, Sora/Manrope fonts bundled in `assets/fonts/`; every visible control must have a real action.
- Comment every class, function and widget with one short line saying what it is or does (Spanish, `///` for public members). New code without that comment is not done.
- Demo accounts (password `biffy123`) and the "Horario de demostración" setting keep the full three-role flow testable offline at any hour; `test/integration/full_flow.dart` drives that flow through the UI.
